# Architecture decision records (living)

| ID | Decision | Why | Status |
|---|---|---|---|
| ADR-001 | Web-first React + R3F | Easy judge access, visual richness, desktop/tablet | Proposed |
| ADR-002 | Pure deterministic TypeScript solver | Testability, credible science, works offline | Proposed |
| ADR-003 | Local guest mode | Privacy, frictionless demo, low cost | Proposed |
| ADR-004 | Optional server-side LLM tutor | Secure key storage, contextual guidance | Proposed |
| ADR-005 | Scope to DC circuitry only | Finish a trustworthy showcase | Proposed |
| ADR-006 | Solver uses nets + nodal analysis (not path search) | A first BFS path-search prototype lit dangling lamps and summed parallel resistance wrongly. Nodal analysis gives correct series/parallel values and KCL. | Accepted 2026-11-15 |
| ADR-007 | Mission 2's fault is reported by the solver as status `NO_PATH` with reason "No energized path from battery to component" (docs/13 names `MISSING_RETURN_PATH`; the solver has no such code and was not changed). Objectives read events derived from solver reports, never UI clicks. | Avoids altering the tested solver contract for a label. Same truth: loop open, lamp dark. | Accepted 2026-11-15 |
| ADR-008 | Persist one versioned blob at `wonderverse:session:v1` (docs/03), Zod-validated and cross-checked against the authored missions on read. Corrupt, oversized or unknown-version data yields a fresh session; unusable single missions are dropped. Undo history is not persisted. | Safe fallback, no crash, no personal data. Reload restores progress and the circuit; undo starts empty. | Accepted 2026-11-15 |
| ADR-009 | Undo is a bounded (50) graph history in `labStore`; redo clears on a new edit. Reset returns to the mission setup, asks for confirmation and is itself undoable. Undo never revokes progress because the mission machine latches objectives and `complete` is absorbing. | Matches FR-10 and R6 (advance once). | Accepted 2026-11-15 |

## Agent change protocol
Before altering a major design decision: document original assumption, alternative, tradeoff, new decision, date and tests. Do not silently substitute a mocked UI for a required engine. After each milestone add: what shipped, tests actually run, unresolved issues, next action.

- **Mission design decisions.**
  1. **M2 fault.** Fixed fixture: the lamp-to-battery-negative wire is missing and the switch starts closed. Success is a learner-caused dark→lit transition (`lampDarkToLit`) plus the correct diagnosis quiz. A lit circuit with no recorded transition does not count. The quiz comes after the repair, as in the existing machine (circuit objectives, then concept check), so "diagnosis" is an explanation of what was wrong, not a pre-fix gate.
  2. **M3 build.** Parts are supplied unwired (one battery, two 6 Ω lamps, a closed switch per lamp). `branchIndependence` needs: a switch opened while ≥2 lamps were lit, then ≥1 still lit and fewer lit than before. A dangling second lamp cannot pass it, and a series build fails it because every lamp goes dark. The series contrast appears in the quiz and recap text, not as a required build step.
  3. **Not done:** the "constrained parts tray" from the PRD is not enforced. The tray still offers every part, so a learner can add extras. Safe limits come from the solver's short-circuit and one-battery guards.
- **Persistence decisions.**
  1. **Stored:** completed ids, low-power setting, and per mission the machine state plus the circuit. No name, id, timestamp, chat or analytics. The mission event log is capped at 1000 events.
  2. **Unknown/corrupt data.** Corrupt data is discarded. A future/unknown schema version is ignored for this run but not deleted until the next save overwrites it (a pristine session removes the key).
  3. **Pristine visit.** A session with nothing to keep stores no key at all.
  4. **Tamper note.** Local progress can be edited by the user (docs/08); loaded missions are checked against the authored objectives, hints and options, but this is not authoritative grading.
  5. **Migration.** There is only v1, so no migration code exists yet. A version bump must add a migrator before shipping.
  6. **Erase.** "Erase my progress" (mission map, with confirm dialog) removes every key starting with `wonderverse:`, resets all stores and announces the result in an `aria-live` region. It reports failure if a key could not be removed.
  7. **Storage failures.** A missing, blocked or full localStorage is caught. The map shows a notice, and the app keeps working in memory.
- **Undo/redo/reset semantics.**
  1. **Scope.** Every graph edit through `dispatch` is a history step, including switch toggles and Clear. Reducer no-ops are not recorded. History is bounded to 50 and is cleared by `loadGraph` (mission start, restart, switching missions, restore).
  2. **Progress is latched.** Objectives that were achieved stay achieved after undo, redo or reset, and the quiz phase never goes back. Events are derived from graph diffs, so an undo can add truthful observations (e.g. a switch seen dark) but cannot remove any.
  3. **Completion.** Completion fires once per run and `completed` is a set. After a reload the state restores as `complete`, and replay keeps the mission completed.
  4. **Keyboard.** Shortcuts: Ctrl/Cmd+Z, Shift+Ctrl/Cmd+Z (also Ctrl/Cmd+Y). They are documented in the UI, ignored in text fields, and ignored while a modal dialog is open.

### 2026-11-15 — T10 (grounded tutor, local fallback, optional gateway)
- **Shipped.**
  - **Pure domain** (`src/domain/learning/tutor/`): `schemas.ts` (Zod `TutorContext`, `TutorResponse`, read-only `TutorAdapter`, limits), `context.ts` (`buildTutorContext`), `screen.ts` (question screening and refusal copy), `validate.ts` (response validator), `localTutor.ts`, `resolve.ts` (`resolveHint`). None import stores, React or features (a test checks the imports).
  - **UI/adapters** (`src/features/tutor/`): `TutorPanel` (mounted in `MissionView`, keyed by mission), `remoteTutor.ts` (`createRemoteTutor`, `getConfiguredTutor`).
  - **Gateway** (`services/tutor/`): FastAPI `POST /hint`, `.env.example`, README, 19 pytest tests. Root `.env.example` has `VITE_TUTOR_URL` only.
- **Decisions.**
  1. **Context.** Built only from the report, a graph summary (counts, lamps, switches), objective statuses, hint level, mission id and the last 8 events rendered as templated strings. No timestamps, names or learner text. Strict schema (unknown keys rejected), arrays capped, 6000-character cap. Values are rounded to 3 decimals so quoted numbers match the context exactly. Currents are shown as magnitudes.
  2. **Grounding rule.** Every number in a response must occur in the context (numeric fields, or digits inside context strings such as labels and the authored hint). Number words with units ("three amps") are rejected. Limit: a small integer that happens to appear in a label (for example "1") would pass, so this proves "no invented measurements", not that every sentence is true.
  3. **Validator order (all adapters, local too).** type, length (over 600 characters is rejected, not truncated), active markup (script, iframe, handlers, `javascript:` rejected), strip harmless markup, blocked content (links, emails, personal-info requests, mains/outlet terms, "mission complete" claims, a short profanity list), numeric grounding. The standard safety sentence is exempt from the mains-term check.
  4. **Fallback.** Remote error, timeout (5 s fetch abort, 6 s outer race), bad shape or failed validation → LocalTutor, labelled "Local guide · offline hint". If even the local text fails validation, a static message is shown. Unsafe, prompt-injection and off-topic questions are answered locally and never sent to a remote adapter.
  5. **Hint ladder.** The tutor has its own 3-step ladder in `TutorPanel` (level n of 3, capped, button disabled at the cap). Refusals do not use up a step. The existing HUD authored-hint ladder is unchanged and independent, so both can show the same authored line. They were not merged, to keep T06-T09 tests and behaviour intact. Tutor steps are not written to the mission event log, and the tutor writes nothing to any store.
  6. **LocalTutor.** Level 1: report observation plus a guiding question (docs/05 examples) plus authored hint 1. Levels 2 and 3: observation plus authored hint 2 or 3. When all objectives are met it points to "Finish mission". It never claims completion itself.
  7. **Gateway.** Key only from `TUTOR_API_KEY`. No key → 503. Order of checks: rate limit, body size, schema, key, provider. CORS allowlist (`*` is ignored), no credentials. Question is passed to the provider as a JSON data field. Provider errors are never echoed.
  8. **No provider is implemented.** `StubProvider` is a labelled placeholder that answers 503, so no vendor or model claim is made. A deployer must add a vetted `Provider` before the AI mode can answer.
  9. **Tests-only helper.** `src/features/tutor/testSupport.ts` exists for tests and is not imported by app code.
- **Tests run (actual).** `npx tsc -b` clean. `npm run lint` clean. `npm run test:run` → 188 passed in 20 files (150 before, 38 new: 28 domain tutor incl. fast-check grounding over random wiring, 4 remote adapter, 6 TutorPanel). `npm run build` passes (same LabScene chunk-size warning). `pytest` in a throwaway venv under /tmp (fastapi, httpx, pytest installed there, not in the repo) → 19 passed.

The keyword screen is a heuristic and can misclassify a question in either direction.

## Live AI tutor through a Vercel function (2026-11-16)
- **Primary gateway is now `POST /api/hint`, a Vercel Node.js function.** User choice: Vercel serverless, providers OpenAI, Anthropic, Google Gemini and OpenRouter, all selectable by `TUTOR_PROVIDER`. `services/tutor` (FastAPI) stays in the repo and in CI, and `VITE_TUTOR_URL` still points the browser at it, but it has no real provider and is now secondary. No SDK dependency: each provider is called with `fetch`.
- **Deviation: the function is `api/hint.js`, a generated bundle, not a hand-written `api/hint.ts`.** Vercel runs files under `api/` unbundled, and this repo is `"type": "module"` with extensionless imports (`moduleResolution: bundler`). The handler imports the shared Zod `TutorContext` and `screen.ts` from `src/domain/learning/tutor`, which pull in the solver types through extensionless imports, so a plain `api/hint.ts` would build green and then fail with "Cannot find module" in production (a known failure with this setup; see the Vercel Node.js runtime page and the community reports of ERR_MODULE_NOT_FOUND on `api/` files). Fix: the source lives in `server/tutor/` (strict TypeScript, typechecked by `tsc -b`, unit-tested by Vitest), and `scripts/build-api.mjs` bundles `server/tutor/entry.ts` with esbuild into one self-contained ESM file `api/hint.js` (83.7 kB minified, zod inlined, no relative imports). `npm run build` regenerates it before `vite build`, the file is committed so Vercel sees it before any build step runs, and `server/tutor/bundle.test.ts` fails if the committed file differs from a fresh bundle and also loads it in plain Node ESM (405 for GET, 422 for an empty context). esbuild was already installed through Vite; it is now an explicit devDependency (0.25.12) because the script imports it. The handler uses Vercel's Web Standard export (`export default { fetch(request) }`), so `@vercel/node` is not needed. `vercel.json` gets `functions["api/hint.js"].maxDuration = 15` (the provider call is capped at 8 s).
- **Request pipeline (cheap checks first, no provider call until all pass):** method (405, `Allow: POST`) -> Origin allowlist (403) -> per-IP rate limit (429, `Retry-After`) -> body cap, 8 KiB, enforced on the declared length and while streaming (413) -> JSON parse and strict Zod parse of `{context, question?}` with the same `TutorContext` as the browser (422) -> question normalised and screened with the same `screen.ts` rules (422 `question_not_allowed`, so unsafe, injection and off-topic text never reaches a model) -> provider, model and key present and valid (503 `tutor_unavailable`) -> provider call with an 8 s abort (504 on timeout, 502 on upstream error) -> server-side `validateTutorText` on the reply (502 `tutor_bad_reply`) -> `200 {text, source: 'ai'}`. Errors carry only a code. The function never logs, and never echoes provider bodies. A test spies on every `console` method to pin that.
- **Origin check.** `TUTOR_ALLOWED_ORIGINS` is a comma-separated list of exact origins; unset means only `https://wonderverse-ai.vercel.app`; `*` is ignored. A request that has an `Origin` header outside the list gets 403; a request with no `Origin` (curl, server to server) is let through, because a non-browser client can set any header, so the Origin check is a guard against other websites using the visitor's browser, not an authentication step. The rate limit and size caps are what protect the endpoint from those clients. Preview deployments have other origins, so the tutor is off there unless their origin is added. An allowed origin gets `Access-Control-Allow-Origin` and a 204 preflight; nothing else does.
- **Rate limit is in memory, per function instance, best effort.** 20 requests per minute per client IP by default (`TUTOR_RATE_LIMIT`), IP from the first `x-forwarded-for` entry that Vercel sets, at most 2000 keys. Vercel can run several instances and recycles them, so each instance counts alone and counts reset on a cold start. It blunts one noisy client; it does not cap spend. No paid KV store was added. The owner should set a spend limit with the model provider.
- **No default model.** Provider docs list model names that change (the pages read for this change show different example names for the same provider), and a wrong default would fail silently. `TUTOR_MODEL` is required; without it the function answers 503 and the app uses the Local guide. The model id must match `[A-Za-z0-9._:/-]` (it is placed in the Gemini URL path, so `../` style values are refused).
- **Provider request shapes (read from official docs on 2026-11-16; none was exercised against a live provider, because no key was available to me):**
  - OpenAI Chat Completions, https://developers.openai.com/api/reference/resources/chat : `POST https://api.openai.com/v1/chat/completions`, `Authorization: Bearer`, body `{model, messages:[{role:'developer',...},{role:'user',...}], max_completion_tokens}`; reply `choices[0].message.content`. `max_completion_tokens` is used because the page marks `max_tokens` deprecated and incompatible with o-series models. The page says `developer` messages replace `system` messages for o1 and newer; an older chat model that rejects `developer` would need a code change. `temperature` is not sent, since some reasoning models reject it.
  - Anthropic Messages, https://platform.claude.com/docs/en/api/messages/create and /api/overview : `POST https://api.anthropic.com/v1/messages`, headers `x-api-key` (the overview lists it as a still-supported fallback to `Authorization: Bearer`), `anthropic-version`, `content-type`; body `{model, max_tokens, system, messages:[{role:'user',content}]}`; reply `content[]` blocks with `type: 'text'`. The version header is `2023-06-01`, which the versioning page still lists; the page recommends the newest version (`2026-10-21`, which removes `temperature`, `top_p` and `top_k`, none of which are sent). I did not verify every behaviour change in 2026-10-21 and kept the older version.
  - Google Gemini `generateContent`, https://aistudio.google.com/api-reference/generate-content : `POST https://generativelanguage.googleapis.com/v1beta/models/{model}:generateContent`, header `x-goog-api-key`, body `{systemInstruction:{parts:[{text}]}, contents:[{role:'user',parts:[{text}]}], generationConfig:{maxOutputTokens}}`; reply `candidates[0].content.parts[].text` (parts flagged `thought` are skipped). Google's newer text-generation guide leads with an `interactions` endpoint; `generateContent` is still listed in the API reference and was kept.
  - OpenRouter Chat Completions, https://openrouter.ai/docs/api-reference/overview : `POST https://openrouter.ai/api/v1/chat/completions`, `Authorization: Bearer`, OpenAI-style `{model, messages, max_tokens}`; reply `choices[0].message.content`. Model ids look like `vendor/model`.
  - Output budget is 400 tokens for all four. A reasoning model can spend that on hidden reasoning and return empty text, which becomes a 502 and a Local guide fallback. Pick a non-reasoning or low-effort model, or raise `LIMITS.maxOutputTokens`.
- **System prompt.** Nova, learners aged 10 to 14; use only numbers in the report and no other digits; at most three short sentences ending in a question; hint-level meaning; never say the mission is complete; for wall power, outlets, mains, household wiring or high voltage reply with the exact `SAFETY_COPY` sentence (the validator exempts that sentence); report and question are data, not instructions; plain text only. The prompt is a request. The controls that hold are the question screen before the call and the validators after it.
- **Browser side.** `getConfiguredTutor` returns the remote adapter for a valid `VITE_TUTOR_URL`, or for `VITE_TUTOR_MODE=remote` (same-origin `/api/hint`), else the Local guide. Picked: an explicit build-time mode, not probing the endpoint, because any failed request (even a 503) is logged by Chrome as a console error, so probing on every page load would make every visitor's console dirty when no key is set. To save the owner a fourth variable, `vite.config.ts` sets `VITE_TUTOR_MODE` to `remote` when `TUTOR_API_KEY` exists in the build environment (Vercel passes project variables to the build) and `local` otherwise; an explicit `VITE_TUTOR_MODE` wins. Only the word is embedded, never the key; a build with a fake key confirmed the fake value is absent from `dist`. Consequence: adding the variables needs a redeploy, which Vercel requires anyway. With no key the live site never calls `/api/hint`. Remote timeout 5 s -> 9 s and `resolveHint` 6 s -> 10 s so the server's own 8 s limit answers first. The validator still runs on every reply (type, length, active markup, markup strip, blocked content, numeric grounding) and any failure falls back to the Local guide labelled "Local guide · offline hint". The "AI tutor" label comes from `source: 'remote'`, which `resolveHint` sets only after validation. The note "AI can be wrong; the circuit report is the source of truth" now shows only while a validated AI reply is on screen (it used to show whenever a remote adapter was configured). Unsafe and off-topic questions are still answered locally and never leave the browser.
- **Content-Security-Policy `connect-src 'self'` added, verified.** The app makes no `fetch` of its own except to the tutor, and loads no third-party script, font, texture or model (fonts are self-hosted `@font-face`, which is `font-src`, not `connect-src`). The policy therefore only blocks the page from talking to any host other than its own (a provider key can never be exfiltrated by injected script to another origin). `vite preview` ignores `vercel.json`, so `vite.config.ts` now serves the same site-wide headers from `vercel.json` in preview; the new E2E test checks the header and then opens the 3D view, so a violation would show in the console guard. It passed on desktop, tablet and mobile. A stricter policy (`default-src`, `script-src`) was not attempted.
- **Tray bug fixed.** The third tray row (`y` 330) was outside the bench (`x` 80..580, `y` 40..250), so a part added there could be moved in but not back. `createComponent` now asks `findFreeCell` (new, in `domain/circuit/layout.ts`, built on `isCellFree` and the bench constants) for a spot: the six authored slots first, then a row-by-row scan of the bench grid, so every new part is in bounds and not overlapping. When no spot is free, `addComponent` returns `null`, changes nothing, records no undo step, and sets the error feedback "The bench is full. Remove a part or move one to make room." With this placement order (six tidy slots first, then the scan) the bench takes 12 parts before it is full, measured by adding lamps until `createComponent` returned `undefined`; that is well above any mission. `createComponent` now returns `undefined` for a full bench; `history.test` used 60 lamp adds to fill the undo history and was rewritten to use switch toggles, because adds now stop at a full bench.
- **Other test and tooling changes.** `src/__tests__/setup.ts` skips the `window` setup when there is no `window`, so `server/**` tests can run in the node environment. `vitest.config.ts` includes `server/**`. `tsconfig.json` includes `server`. E2E: the Playwright build now runs with `VITE_TUTOR_MODE=remote`, an auto fixture answers `**/api/hint` with 503 by default (like a deployment with no key), tests register their own route for AI replies, and the one Chrome network line for that 503 is allowlisted with a reason. Against a deployed site (`E2E_BASE_URL`) the route-dependent tests are skipped unless `E2E_TUTOR_REMOTE=1`, because the build mode is not known.
- **Not verified.** No real provider was called, so none of the four request shapes has been proven against a live API; the unit tests check the request and parsing against the documented shapes with a mocked `fetch`. The function was loaded in plain Node ESM (bundle test) but not run under `vercel dev`; its behaviour on Vercel is checked after deploy (see docs/18). The model's answer quality, its obedience to the system prompt and its latency are unmeasured; the validators are the only guarantee. No spend control exists in this repo.
## Android pass: blank 3D, schematic fit, mobile layout, Back button (2026-11-18)
- **Why.** A user reported "nothing works as expected" on Android. The Pixel_10_Pro emulator (Android 17, API 37, Chrome and WebView 145.0.7632.218) showed four real problems, each reproduced before any fix: an empty 3D stage with no message; a schematic fixed at 680 px that scrolled sideways (Lamp 1 cut off); the circuit far below header, tour card, toolbar, shortcut text and tray; and the Back button leaving the app from anywhere.
- **Blank 3D: cause.** Two layers. (1) On this emulator `-gpu host` (the GPU the emulator uses by default on this Mac, "Android Emulator OpenGL ES Translator (Apple M3 Pro)") creates a WebGL context and `readPixels` returns the right values, but the canvas is never composited onto the screen. A bare 200 x 200 canvas cleared to green in a page with no framework was blank under `-gpu host` and showed green under `-gpu swiftshader_indirect`. The same WonderVerse build draws the full scene under `swiftshader_indirect`, in Chrome and in a WebView. So the blank box is an emulator GPU artefact, not an app render bug, and no JavaScript can see it (the canvas draws, the browser simply does not show it). (2) The app gave the user nothing to do about it: no message, no fallback. That part is ours and is fixed below.
- **Blank 3D: fix.** (a) `LabScene` has a `FrameProbe` that reports the first rendered frame. `LabWorkbench` starts a 6 s timer (`FIRST_FRAME_TIMEOUT_MS`) whenever the 3D view is showing and no frame has been seen. If it fires, the view switches to the schematic, keeps the circuit, shows "The 3D workbench did not draw anything on this device..." (role alert) and offers Try 3D again. This covers a blocked GPU process, a zero-size canvas and a context that failed quietly. (b) Because a canvas that draws but is not shown cannot be detected, a line directly under the stage reads "Cannot see the 3D bench on this device? Use the schematic instead" with a 44 px button. Under the emulator's `-gpu host` the stage is still empty, now with that button right under it. (c) The stage carries `data-frame="drawn|waiting"`, which the E2E helper uses so 3D hover tests wait for the first frame (a documented desktop flake).
- **Schematic.** The svg is `w-full h-auto` over a fixed viewBox `-32 0 724 H` (`stageScale.ts`), so it always fits the container. Positions stay in model units; pointer positions are mapped with the svg's own screen matrix, so letterboxing is handled. Scaling alone made targets about 26 px, so: terminal touch circles are sized in model units to be 44.5 CSS px across at any stage width; on a phone two terminals of one part are only about 35 px apart, so each circle is also shifted outward from its part (by about 29 units at 342 px) so it no longer covers the body, which keeps at least an 8 px strip at the part centre for toggling a switch or starting a drag; part bodies have a touch box of at least 44 px; part labels never fall below 11 CSS px. A first attempt with centred 44 px circles made a tap on a switch's centre hit a terminal; the existing touch test caught it. No reflow was needed (the model layout is unchanged, so saved sessions and fixtures keep working). On a phone held sideways (height 500 px or less) the svg is capped at 165 px tall and letterboxed.
- **Mobile layout.** Below 640 px: toolbar is two rows (view toggle with How to play; Undo, Redo, Reset with icons and short labels, accessible names unchanged); the keyboard shortcut sentence is visually hidden on `pointer: coarse` and the status sentence is screen-reader only below `sm`; the tray is a three-column grid of icon buttons placed right under the stage (it was above the schematic); the tour is a fixed bottom coachmark (max 55% of the height, with spacer so content stays reachable) instead of a card in the flow; the long instructions sit behind "Help" buttons (`Collapsible`, closed by default on phones, always open from 640 px); objectives and Ask Nova are collapsible below 1024 px but open by default (tests and keyboard users keep today's behaviour); header buttons read "Missions" and "Start" (accessible names unchanged); feedback bar becomes a floating bottom bar in short landscape. Tailwind note: adding a raw `short` screen to the config silently turned off every `max-sm:` utility, so the short-landscape rules use the arbitrary variant `[@media(max-height:500px)]:`. Nothing here depends on there being only one lab: `LabWorkbench` takes a `toolbarExtra` slot and the toolbar, tray and stage are generic.
- **Android Back.** `src/app/backStack.ts`. Each screen (start, map, mission) is a history entry; an open dialog or the tour adds one entry and Back pops it. Closing by button pops the entry that overlay added (never another). In tests the hook is covered in jsdom and in Chromium (`page.goBack()`); on the emulator the real hardware Back key (`adb shell input keyevent BACK`) was used. Known limit: leaving a screen while the tour is open leaves one stale entry (one extra Back does nothing visible).
- **WebView.** A 5 KB shell APK was built outside the repo with only the SDK (aapt2, javac, d8, zipalign, apksigner, a keytool debug key; no Gradle). It enables JavaScript, DOM storage and debugging. WebView-specific findings: the app needs DOM storage; with it off `window.localStorage` throws, the app still runs with no console error and shows its existing "storage" notice on the map (verified); the system font scale (1.3) is applied inside a WebView (root 20.8 px) but not inside Chrome's page text; a WebView activity that does not handle Back would close, so the shell goes back in web history first (the shell is test tooling, not part of the product).
- **Not done / not verified.** No physical Android device; GPU: only the emulator's host GPU (blank canvas) and SwiftShader. Soft keyboard: see docs/18 for what was measured. Chrome page text scaling follows Chrome's own accessibility setting, not the system font scale, so font scale 1.3 was exercised in the WebView only. TalkBack not run.
